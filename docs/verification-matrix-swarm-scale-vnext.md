## Why this exists

Implementation beads in `bd-2mb03` add concurrent, observability, and
gating behavior that is hard to verify with unit tests alone. Without a
shared matrix, agents tend to rely on proxy signals (build green,
package compiles) and miss regressions in latency, memory, contract
shape, and replay fidelity. This matrix anchors verification to
concrete commands, artifacts, and triage notes so each gate has the
same semantics across agents.

## Gate taxonomy

Every gate falls into one of three categories. Each implementation bead
declares which gates apply to it (see the per-bead checklist below).

| Gate         | Purpose                                              | Default invocation |
|--------------|------------------------------------------------------|--------------------|
| `short`      | Deterministic correctness; runs in `-short` mode.    | `go test -short ./...` |
| `race`       | Concurrency correctness on touched packages.         | `go test -race ./internal/<pkg>/...` |
| `load`       | Opt-in 100-pane synthetic swarm.                     | `NTM_SYNTHETIC_SWARM_LOAD=1 go test -run 'OptInWritesArtifact' -timeout 10m ./internal/swarm/` |

There is no `bench` gate: no swarm-scale package defines a Go benchmark
today, and the previous matrix cited a gate benchmark that never
existed (the same fictional evidence that condemned the pressure
governor under C8 — see "Removed rows" below). A bench gate may be
reintroduced only together with the benchmark it cites.

`short` runs locally; `race` may go through `rch exec -- go test -race
...` on contended machines; `load` is opt-in via
`NTM_SYNTHETIC_SWARM_LOAD=1` and is entirely synthetic — no tmux
server, no real agent CLIs.

## Scale reality

The synthetic load harness runs **100 panes** — pinned by the
`load_100_pane` experiment scenario in `internal/swarm/synthetic.go`
and asserted end-to-end by `TestSyntheticHarnessLargeOptInWritesArtifact`
(pane_count exactly 100, event_count exactly 500). The conformance test
reads the scenario's `PaneCount` from the harness itself and fails this
document if the figure here ever drifts from the code. Any claim above
100 panes requires actually raising the harness and committing the run
log in the same PR.

## Logging requirements

Every gate writes structured log lines (slog) with these correlation
fields (omitted only when not applicable):

- `test_run_id` — ID generated by the harness once per matrix run.
- `gate` — one of `short|race|load`.
- `feature` — the bead-id of the feature under test (e.g. `bd-2mb03.2`).
- `session` — synthetic swarm session name when applicable.
- `pane_count` — total synthetic panes active.
- `command_count` — robot commands issued during the gate.
- `event_count` — synthetic output events handled.

## Artifact formats

Load-gate artifacts are written by `SyntheticRunResult.WriteArtifact`
(see `internal/swarm/synthetic.go`) and the experiment lab's versioned
artifact writer; `TestSyntheticExperimentWritesVersionedArtifactsAndLogs`
pins the format. Both include pane/command/event counts, latency, and
memory-growth metrics; the experiment artifacts are versioned and
robot-readable (`TestSyntheticExperimentSummaryIsRobotReadable`).

## Run sequencing

A full matrix run executes gates in this order to fail fast:

1. `short` for every bead in scope.
2. `race` for beads marked Required.
3. `load` once per matrix run, with `NTM_SYNTHETIC_SWARM_LOAD=1`.

## Required vs no-real-model paths

- **No real model:** every `short` and `race` gate runs entirely with
  the synthetic harness; no real Claude / Codex / Antigravity / Gemini
  CLI is launched. This is mandatory for matrix reproducibility.
- **Opt-in 100-pane:** the `load` gate drives 100 synthetic panes in
  `./internal/swarm/`. Triggered only when `NTM_SYNTHETIC_SWARM_LOAD=1`
  is exported.

A future agent who wants only the no-real-model gates can run:

```bash
go test -short ./internal/swarm/ ./internal/robot/contract/ ./internal/robot/ ./internal/cli/ ./internal/coordinator/
```

## Surfacing this matrix in `bv --robot-triage`

Adding this matrix bead must not hide implementation work. Verify with:

```bash
bv --robot-triage | jq '.recommendations | length'
```

The count must remain >= the count before this matrix bead landed; if
it drops, an implementation bead inadvertently became dependent on
this verification bead and the dependency must be reversed.

## Change control

Edits to this matrix follow the same workflow as code:

1. Open a bead under `bd-2mb03` (or the reality-bridge program)
   referencing the change reason.
2. Update this file.
3. Run `go test ./tests/ -run TestMatrix` — the conformance test must
   pass, which forces every newly cited gate to actually exist.
4. `br sync --flush-only && git add docs/verification-matrix-swarm-scale-vnext.md .beads/issues.jsonl && git commit`.

This document supersedes any inline test-strategy comments inside
swarm-scale beads.
